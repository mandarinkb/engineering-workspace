# บทที่ 3: Dead Letter Queue (DLQ)

## 3.1 ทำไม Message ถึงประมวลผลล้มเหลวซ้ำๆ

ในโลกจริง consumer ไม่สามารถประมวลผล message ได้สำเร็จ 100% เสมอไป สาเหตุแบ่งได้เป็นสองกลุ่มใหญ่ที่ต้องรับมือต่างกัน:

- **Poison message** — message ที่มีรูปแบบผิดปกติจนไม่มีทางประมวลผลสำเร็จได้เลย ไม่ว่าจะ retry กี่ครั้ง (เช่น JSON เสียรูปแบบ, field ที่ควรเป็นตัวเลขกลับเป็นตัวอักษร, ข้อมูลอ้างอิงถึง entity ที่ไม่มีอยู่จริงและไม่มีวันมีอยู่) — เรียกว่า "poison" เพราะมันเป็นพิษต่อ consumer: ถ้า consumer ไม่มีกลไกจัดการ จะพยายาม retry message นี้**ไม่มีที่สิ้นสุด** ค้างอยู่ตรงนั้นตลอดไป
- **Bug ในโค้ด consumer** — โค้ดประมวลผลมี edge case ที่ไม่ได้ handle (เช่น null pointer เมื่อ field หนึ่งไม่มีค่า) ทำให้ message บางรูปแบบล้มเหลวเสมอจนกว่าจะแก้โค้ด
- **Transient downstream outage** — ความล้มเหลวชั่วคราวที่ไม่เกี่ยวกับตัว message เลย เช่น database ที่ consumer ต้องเขียนผลลัพธ์ลงไปล่มชั่วคราว, downstream API timeout — message นี้อาจประมวลผลสำเร็จได้ถ้า retry อีกครั้งหลังจากรอสักพัก (ต่างจาก poison message ที่ retry เท่าไหร่ก็ไม่มีวันสำเร็จ)

### ปัญหาของ Partition ที่ Consumer ยัง Retry ค้างอยู่

จุดที่ทำให้เรื่องนี้ร้ายแรงกว่าที่คิดคือ ถ้า consumer เจอ message ที่ล้มเหลวแล้ว**ไม่ commit offset ต่อ** (เพื่อรักษา at-least-once ตามที่กล่าวใน [บทที่ 2](02-partition-and-consumer-group.md)) แล้วพยายาม retry message เดิมซ้ำๆ ไม่มีที่สิ้นสุด — **message ทุกตัวที่มาทีหลังใน partition เดียวกันจะติดคอรอตามไปด้วย** (เพราะ ordering ภายใน partition ต้องประมวลผลเรียงลำดับ) กลายเป็นว่า message หนึ่งตัวที่มีปัญหาสามารถบล็อกทั้ง partition ได้ ทำให้ consumer group ทั้งกลุ่มหยุดคืบหน้าไปข้างหน้าเลย แม้ message อื่นๆ ที่ตามมาจะไม่มีปัญหาอะไรก็ตาม

ทางเลือกอีกด้านคือ**ข้าม (skip) message ที่ล้มเหลวไปเฉยๆ** โดย commit offset ต่อไปเหมือนไม่มีอะไรเกิดขึ้น — วิธีนี้แก้ปัญหา partition ติดคอได้จริง แต่แลกมาด้วยการ**สูญเสีย message นั้นไปอย่างเงียบๆ** ไม่มีใครรู้ว่ามันหายไป จนกว่าจะมีคนมาสังเกตเห็นความผิดปกติภายหลัง (เช่น ยอดขายไม่ตรง, ลูกค้าโทรมาถามว่าทำไม order ไม่เข้าระบบ) ทั้งสองทางเลือกนี้ (บล็อกตลอดไป vs หายเงียบๆ) ไม่มีทางไหนยอมรับได้ในระบบ production จริง

## 3.2 Dead Letter Queue Pattern

**Dead Letter Queue (DLQ)** แก้ปัญหานี้ด้วยทางเลือกที่สาม: เมื่อ message ล้มเหลวซ้ำเกินจำนวนครั้งที่กำหนด **ย้ายมันออกจาก topic เดิมไปเก็บไว้ที่ topic แยกต่างหาก** (DLQ topic) แล้ว**เดินหน้าต่อ**กับ message ถัดไปในลอกเดิมทันที:

```
Topic "orders" (ปกติ):

  [M1: ok][M2: ok][M3: poison!][M4: ok][M5: ok]...
                       │
                       │ retry 3 ครั้งแล้วยังล้มเหลว
                       ▼
              ย้ายไป Topic "orders-dlq"
                       │
  consumer เดินหน้าต่อกับ M4, M5, ... ทันที (ไม่ติดคอ)
```

ข้อดีของแนวทางนี้คือได้ทั้งสองอย่าง: **partition ไม่ติดคอ** (message ที่ตามมายังประมวลผลต่อไปได้) และ **ไม่มี message ไหนหายไปเงียบๆ** (ทุกตัวที่ล้มเหลวยังอยู่ใน DLQ topic ให้ตรวจสอบและแก้ไขภายหลังได้)

## 3.3 ออกแบบ Retry-Topic + DLQ-Topic Pipeline

ในทางปฏิบัติมักไม่ย้าย message ไป DLQ ทันทีตั้งแต่ล้มเหลวครั้งแรก เพราะความล้มเหลวชั่วคราว (transient) สมควรได้โอกาส retry ก่อน — pattern ที่นิยมคือแยก topic เป็นหลายชั้นตามจำนวนครั้งที่ retry พร้อม backoff ระหว่างแต่ละชั้น:

```
orders (topic หลัก)
   │ ล้มเหลวครั้งที่ 1
   ▼
orders-retry-1 (รอ 30 วินาทีก่อนประมวลผล)
   │ ล้มเหลวอีก
   ▼
orders-retry-2 (รอ 5 นาทีก่อนประมวลผล)
   │ ล้มเหลวอีก
   ▼
orders-retry-3 (รอ 30 นาทีก่อนประมวลผล)
   │ ล้มเหลวอีก (ครบจำนวนครั้งที่กำหนดแล้ว)
   ▼
orders-dlq (เก็บถาวร รอการตรวจสอบโดยคน)
```

แต่ละ retry topic มี consumer ของตัวเองที่ **delay ก่อนประมวลผล** (ตาม backoff strategy ที่เพิ่มขึ้นเรื่อยๆ แนวคิดเดียวกับ exponential backoff ใน [Volume 11 — Retry](../11-microservices/04-saga-and-resilience.md)) — การแยกเป็นหลาย topic แบบนี้ (แทนที่จะ retry วนอยู่ใน topic เดิม) ทำให้ message ที่กำลังรอ backoff ไม่ไปบล็อก message ปกติที่ยังไม่เคยล้มเหลวเลยที่กำลังไหลเข้ามาใน topic หลักอย่างต่อเนื่อง

ควรแนบ **metadata** ไปกับ message ตอนย้ายระหว่าง topic เสมอ เพื่อให้ตรวจสอบภายหลังได้ง่าย เช่น จำนวนครั้งที่ retry ไปแล้ว, error message ล่าสุด, timestamp ที่ล้มเหลวแต่ละครั้ง, topic ต้นทางเดิม — ข้อมูลเหล่านี้จำเป็นมากตอนต้องสืบสวนว่า message ใน DLQ ล้มเหลวเพราะอะไรกันแน่

## 3.4 การปฏิบัติงานจริง: Monitoring และ Replay

### Monitor DLQ Depth

DLQ ไม่ใช่ที่ "ทิ้งแล้วลืม" — จำนวน message สะสมใน DLQ topic (**DLQ depth**) คือ metric สำคัญที่ต้อง monitor และตั้ง alert (เชื่อมกับ [Volume 14 — Observability](../14-observability/README.md)) เพราะ:

- DLQ depth ที่เพิ่มขึ้นเรื่อยๆ อย่างต่อเนื่องมักบ่งชี้ **bug ใหม่ที่เพิ่ง deploy** หรือ **downstream dependency ที่ล่มเป็นวงกว้าง** ไม่ใช่แค่ poison message เดี่ยวๆ ประปราย
- ถ้าไม่ monitor เลย DLQ จะกลายเป็น "หลุมดำ" ที่ message หายเข้าไปเรื่อยๆ โดยไม่มีใครรู้ตัว จนกว่าจะมีคนมาสังเกตเห็นผลกระทบทางธุรกิจ ซึ่งอาจสายเกินไปแล้ว

แนวทางปฏิบัติที่ดีคือตั้ง alert แบบ**อัตราการเพิ่มขึ้น** (rate of growth) ไม่ใช่แค่จำนวนสัมบูรณ์ (เช่น "DLQ เพิ่มขึ้นเกิน 100 message ใน 5 นาที" มีความหมายกว่า "DLQ มี 1,000 message" เฉยๆ เพราะบางระบบมี baseline ของ DLQ ที่ไม่เป็นศูนย์อยู่แล้วตามปกติจาก edge case เล็กน้อยที่ทราบสาเหตุแล้ว)

### Replay จาก DLQ หลังแก้ไขต้นตอแล้ว

เมื่อสืบสวนพบสาเหตุและแก้ไขแล้ว (แก้ bug ในโค้ด, downstream กลับมาทำงานปกติ) ขั้นตอนสุดท้ายคือ **replay** — อ่าน message จาก DLQ topic แล้วส่งกลับเข้าไปประมวลผลใหม่อีกครั้ง (มักส่งกลับเข้า topic หลักตัวเดิม หรือ topic พิเศษสำหรับ replay โดยเฉพาะเพื่อแยกจาก traffic ปกติ)

ข้อควรระวังตอน replay:

- **Replay ทีละน้อยก่อน** ไม่ใช่ dump ทั้งหมดกลับเข้าไปทันที เพื่อยืนยันว่าการแก้ไขได้ผลจริงก่อนปล่อย volume ใหญ่ตามไป (ป้องกันไม่ให้ปัญหาเดิมเกิดซ้ำกับ message ทั้งชุด)
- **ตรวจสอบ idempotency ของ consumer** ก่อน replay เสมอ (เชื่อมกับ [Volume 11 — Idempotency](../11-microservices/05-idempotency-and-tracing.md)) เพราะ message บางตัวใน DLQ อาจเคยประมวลผลสำเร็จไปบางส่วนแล้วก่อนที่จะล้มเหลว (เช่น เขียน database สำเร็จแต่ส่ง notification ไม่สำเร็จ) การ replay ซ้ำโดยไม่ idempotent อาจทำให้เกิดผลข้างเคียงซ้ำซ้อน
- **เก็บ message ที่ replay ไม่สำเร็จอีกไว้แยกต่างหาก** ไม่ใช่ย้อนกลับเข้า DLQ เดิมปนกับของใหม่ เพื่อไม่ให้สับสนระหว่าง "รอบเก่าที่ยังไม่แก้" กับ "รอบใหม่ที่ replay แล้วยังไม่ผ่าน"

## สรุปย่อ

| แนวคิด | ประเด็นสำคัญที่สุด |
|---|---|
| Poison message | message ที่ไม่มีทางประมวลผลสำเร็จได้เลยไม่ว่า retry กี่ครั้ง |
| ปัญหาถ้าไม่มี DLQ | retry ค้างไม่มีที่สิ้นสุดบล็อกทั้ง partition หรือ skip แล้วเสีย message เงียบๆ |
| DLQ pattern | ย้าย message ที่ล้มเหลวซ้ำไป topic แยก แล้วเดินหน้าต่อกับ message ถัดไปทันที |
| Retry-topic pipeline | แยก topic เป็นหลายชั้นตามจำนวนครั้ง retry พร้อม backoff เพิ่มขึ้นเรื่อยๆ ก่อนถึง DLQ จริง |
| Metadata ที่ต้องแนบ | จำนวนครั้ง retry, error ล่าสุด, timestamp, topic ต้นทาง — จำเป็นตอนสืบสวน |
| Monitor DLQ depth | ดูอัตราการเพิ่มขึ้น ไม่ใช่แค่จำนวนสัมบูรณ์ บ่งชี้ bug ใหม่หรือ downstream ล่มเป็นวงกว้าง |
| Replay จาก DLQ | ทำทีละน้อยก่อน ตรวจสอบ idempotency ของ consumer ก่อนเสมอ |

## คำถามทบทวน

1. อธิบายว่าทำไม message หนึ่งตัวที่ล้มเหลวถึงสามารถบล็อกทั้ง partition ได้ ถ้า consumer พยายาม retry ไม่มีที่สิ้นสุด
2. เปรียบเทียบสองทางเลือกที่ไม่มี DLQ (retry ค้างตลอดไป vs skip แล้วเสีย message) ว่าทำไมทั้งคู่ยอมรับไม่ได้ในระบบ production
3. ทำไมการออกแบบ retry-topic หลายชั้นพร้อม backoff ถึงดีกว่าการ retry วนอยู่ใน topic เดิม
4. ทำไมการ monitor DLQ depth ควรดูที่ "อัตราการเพิ่มขึ้น" มากกว่า "จำนวนสัมบูรณ์"
5. ก่อน replay message จาก DLQ กลับเข้าระบบ ต้องตรวจสอบอะไรบ้าง และทำไมเรื่อง idempotency ถึงสำคัญตรงจุดนี้
