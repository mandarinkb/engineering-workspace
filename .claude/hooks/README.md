## 2. ข้อเสนอการออกแบบให้ subagent ทำงานรวมกันอย่างมีประสิทธิภาพ

อ่านจาก: `.agents/README.md`, `.agents/workflows/ticket.md`, `.claude/agents/*.md` (อ่านเฉพาะส่วนต้นของไฟล์ agent) และสรุปหน้าเว็บ
[AI-native SDLC playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)

### 2.1 ข้อจำกัดของข้อเสนอนี้ (อ่านก่อน)

- **ไม่มีข้อมูลการรันจริงให้วัด:** โฟลเดอร์ `reviews/` ถูก gitignore และผู้ใช้ลบทิ้งได้ ผมค้นใน `.scratch/` แล้วไม่พบ `log.tsv` สักไฟล์ ข้อเสนอด้านล่างจึงเป็น **สมมติฐานจากการอ่านดีไซน์** ไม่ใช่ผลวัดว่าจุดไหนช้าหรือแพงจริง
- ไม่ได้อ่าน `ticket.md` ที่เหลือหลังหัวข้อ "สิ่งที่ยังไม่ได้ติดตั้ง" และไม่ได้อ่าน template ทั้งหมด

### 2.2 สิ่งที่ออกแบบไว้ดีแล้ว (ไม่แนะนำให้แตะ)

- **หนึ่ง spawn = หนึ่งขั้น และส่งต่อผ่าน lead เท่านั้น** ไม่มี subagent ค้างรอ ไม่มีการคุยกันเอง ลดปัญหา context ปนกัน
- **qa เขียน Bruno แบบ blind ขนานกับ backend** ได้ทั้งความเร็วและความเป็นอิสระของผู้ตรวจ ตรงกับหลัก "ผู้เขียนอนุมัติงานตัวเองไม่ได้" ของ playbook
- **แยกระดับความเสี่ยงเพื่อเลือกผู้ตรวจ** (spec-reviewer เฉพาะ ticket เสี่ยง) ประหยัดโดยไม่ลดการตรวจที่จำเป็น
- **หลักฐานเป็นไฟล์ + brief เป็นไฟล์ + `progress.md`/`log.tsv`** ทำให้ resume หลัง session หลุดได้ และ lead ไม่ต้องแบก output เต็มใน context
- **retry ตามประเภทความล้มเหลว และเพดาน 3 รอบ** กัน loop ไม่รู้จบ
- **เครื่องมือถูกจำกัดต่อ role** (`disallowedTools`) และ `Agent` ถูกปิดทุก role จึงไม่มี spawn ซ้อน
- ในเซสชันนี้ Claude Code ค้นเจอ role ครบทั้ง 4 ตัว (analyst, backend, qa, spec-reviewer) ซึ่งตอบข้อที่ `.agents/README.md` เคยเขียนว่า "ยังไม่รู้" ได้ส่วนหนึ่ง

### 2.3 ข้อเสนอ เรียงตามความคุ้มที่ผมคาด

**1) ทำ "digest" ของ ticket หนึ่งไฟล์ แล้วให้ทุก brief ชี้ไปที่เดียว**
- ปัญหา: ทุก spawn ต้องอ่าน `AGENTS.md` + ticket ใหม่ และ AC ถูกตีเลขหลายที่ (`spec-reviewer.md` ให้ตีเลข AC-1, AC-2 ตามลำดับที่เจอ ส่วน qa ระบุ AC ใน `docs` ของแต่ละ request) เลขอาจไม่ตรงกัน ทำให้เทียบรายงานข้าม role ยาก
- ข้อเสนอ: lead เขียน `digest.md` ครั้งเดียวตอนสรุปแผน (ขั้น 1) ประกอบด้วย AC ที่ตีเลขแล้ว, contract, รายการไฟล์ที่อนุมัติ, คำตัดสินของผู้ใช้, AC ที่พิสูจน์ใน session ไม่ได้ ทุก role ใช้เลข AC ตามไฟล์นี้
- ข้อแลกเปลี่ยน: lead ต้องเขียนเพิ่มหนึ่งไฟล์ และ digest ที่ผิดจะผิดพร้อมกันทุก role จึงต้องให้ผู้ใช้เห็นก่อน spawn (ซึ่งขั้น 1 มี gate ผู้ใช้ยืนยันอยู่แล้ว)

**2) ให้ความหนักของกระบวนการเปลี่ยนตามความเสี่ยง ไม่ใช่แค่เปลี่ยนผู้ตรวจ**
- ตอนนี้ ticket ปกติที่เล็กมากก็ยังมี brief file, `log.tsv`, `progress.md`, `evidence.md`, qa หลาย spawn และ lead รัน mutation ซ้ำ
- ข้อเสนอ: นิยามเลน "เล็ก" (เช่น แตะ ≤ 2 ไฟล์ ไม่เข้าเกณฑ์เสี่ยงข้อใดเลย) ที่ข้ามหรือรวมบางขั้น เช่น รวมขั้น 3 กับ 4 (workflow อนุญาตอยู่แล้ว) และบันทึก `log.tsv` เฉพาะการตัดสินใจ ไม่บันทึกทุก spawn
- ข้อแลกเปลี่ยน: เลนเล็กที่นิยามหลวมจะกลายเป็นช่องโหว่ ต้องมีกติกา "เลื่อนขึ้นเป็นเสี่ยงทันที" เหมือนที่มีอยู่แล้ว และ **ไม่ควรทำข้อนี้ก่อนมีข้อมูลตามข้อ 5**

**3) แก้วนรอบเล็กด้วย backend ตัวเดิม (ทางเลือก ไม่ใช่ข้อบังคับ)**
- ตอนนี้ fix item ทุกรอบ spawn backend ตัวใหม่ ซึ่งต้องอ่านโค้ดและ ticket ใหม่ทั้งหมด
- ข้อเสนอ: ถ้า fix item เล็ก (1–2 ไฟล์ ไม่มี decision request) ส่งต่อให้ตัวเดิมผ่าน `SendMessage` (ใช้ agent ID) เพื่อใช้ context เดิม
- ข้อแลกเปลี่ยนที่ต้องชั่ง: ดีไซน์ปัจจุบันเลือก spawn ใหม่และ "ไม่ตั้ง `name`" โดยตั้งใจ (กัน context เก่า และกัน Agent Teams) ผมยังไม่ได้ทดสอบว่าวิธีนี้ทำงานกับ subagent ที่ไม่ได้ตั้งชื่อในเครื่องนี้ และมันขัดกับข้อ "หนึ่ง spawn = หนึ่งขั้น" ต้องแก้ workflow ด้วย

**4) ขนานหลาย ticket ได้ แต่ต้อง queue ขั้นรัน qa**
- `ticket.md` เขียนเองว่า "ทบทวนเมื่อรันหลายงานอิสระพร้อมกัน" ถ้าจะทำ ส่วน implement และ review แยกได้ด้วย worktree (`isolation: "worktree"` ของเครื่องมือ Agent)
- แต่ขั้น qa รันใช้ทรัพยากรร่วม: server local พอร์ตเดียว, สมาชิกทดสอบคนเดียว (`REG_ST_IDENTIFIER_*`) และโควตา OTP 5 ครั้ง/5 นาที/identifier ที่ workflow ระบุไว้ รัน qa ขนานจะชนกันและเกิด `BLOCKED`
- ข้อเสนอ: ขนานได้เฉพาะ implement/review ส่วน qa รันเรียงทีละ ticket โดย lead เป็นคนคุมคิว

**5) วัดก่อนปรับ (ควรทำก่อนข้อ 2 และ 3)**
- ปัญหา: `reviews/` ถูกลบ จึงไม่มีข้อมูลย้อนหลัง
- ข้อเสนอ: ก่อนลบ `reviews/<ticket>/` ให้ lead เขียนสรุปหนึ่งบรรทัดลง `## Comments` ของ ticket: จำนวน spawn, จำนวนรอบแก้, สาเหตุที่วน, ขั้นที่ใช้เวลามากสุด เก็บ 5–10 ticket แล้วค่อยตัดสินว่าข้อ 2 และ 3 คุ้มหรือไม่
- ตรงกับ playbook ที่แนะนำชุด eval จากงานจริง (20–50 งาน) และรันซ้ำเมื่อแก้ไฟล์ agent/skill ticket เก่าที่จบแล้ว (เช่น 06 และ 47 ที่ workflow อ้างเป็นบทเรียน) เป็นตัวเลือกแรกของชุดนั้น

**6) เรื่องโมเดล: ยังไม่แนะนำให้เปลี่ยน**
- ทุก role ใช้ `sonnet` อยู่ และ `.agents/README.md` ระบุทางเลือก `opus` สำหรับ spec-reviewer เฉพาะงานเสี่ยงสูงไว้แล้ว ซึ่งเหมาะสม
- การลดเป็นโมเดลเล็กกว่าสำหรับ analyst หรือ qa (ขั้นเขียน) เป็นไปได้ แต่ควรทำหลังมีข้อมูลตามข้อ 5 เท่านั้น เพราะถ้า analyst สรุปผิด ความเสียหายไปตกที่ขั้นหลังทั้งหมด

### 2.4 ลำดับที่แนะนำ

1. ข้อ 5 (วัด) เริ่มได้ทันที ไม่ต้องแก้ workflow
2. ข้อ 1 (digest) ขนาดเล็ก ความเสี่ยงต่ำ ได้ทั้งความเร็วและความสอดคล้องของ AC
3. ข้อ 2, 3, 4 ตัดสินหลังมีข้อมูลจากข้อ 5

### 2.5 เรื่องแยก (ถ้าสนใจภายหลัง): ใช้ hook บังคับกติกาของ subagent

ตอนนี้กติกาอย่าง "ห้าม commit", "ห้าม `gofmt -w` ทั้งโฟลเดอร์" อยู่ในข้อความ prompt อย่างเดียว playbook ชี้ว่า hook คือชั้นที่บังคับได้จริง และ `.agents/README.md` ระบุว่ายังไม่ได้ติดตั้ง `guard_git` (ต้นแบบ crash กับ `git commit -F -`) ไม่ใช่เรื่องประสิทธิภาพการทำงานร่วมกัน จึงแยกไว้ ไม่ได้ลงรายละเอียด
