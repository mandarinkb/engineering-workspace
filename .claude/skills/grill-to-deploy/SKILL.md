# grill-to-deploy

ใช้กับงานที่ต้องผ่านทั้งการออกแบบ โค้ด deploy และพิสูจน์บน stack จริง ทำเรียงตามเฟส แต่ละเฟสจบที่ **เงื่อนไขเสร็จ** ข้ามไปเฟสถัดไปเมื่อเงื่อนไขนั้นเป็นจริงเท่านั้น

คำหลักที่ใช้ในเอกสารนี้: **grill** (ซักจนไม่เหลือข้อสงสัย), **seam** (จุดที่ทดสอบ), **tracer bullet** (ชิ้นงานบางๆ ที่ตัดผ่านทุกชั้น), **frontier** (งานหรือคำถามที่เริ่มได้เลยเพราะตัวที่มันรออยู่เสร็จแล้ว), **red** (test ล้มให้เห็นก่อนแก้)

รายละเอียดที่ไม่ใช้ทุกครั้งอยู่ในไฟล์ข้างๆ — เปิดเมื่อถึงจุดที่ชี้เท่านั้น:
`environment.md` (ข้อเท็จจริงและคำสั่งของ Mini PC) · `implementer-guide.md` (แม่แบบคู่มือให้ subagent) · `testing.md` (Bruno และ Playwright) · `traps.md` (ที่เคยพลาดและกัน)

## 1. Grill

เรียก `grilling` และ `domain-modeling` (ผ่าน `/grill-with-docs`) ถามทีละรอบ ข้อละคำถามพร้อมคำตอบที่แนะนำ หาข้อเท็จจริงจากโค้ดเอง ไม่ถามผู้ใช้ในสิ่งที่ค้นได้ บันทึกศัพท์ลง `GLOSSARY.md` และ ADR (เฉพาะเรื่องที่ย้อนกลับยาก ชวนสงสัย และเป็นการเลือกจากทางเลือกจริง) ทันทีที่ตกลงกัน

**เสร็จเมื่อ:** frontier ของคำถามว่าง และทุกการตัดสินใจถูกเขียนไว้ (glossary, ADR หรือตารางสรุป)

## 2. Spec

เรียก `to-spec` ไม่มี issue tracker (เครื่องนี้ไม่มี `gh`) จึงเขียน `docs/specs/<ชื่อ>.md` ตั้งชื่อ **seam** แล้วให้ผู้ใช้ยืนยันก่อนเขียน: ใช้ seam ที่มีอยู่แล้วและอยู่สูงที่สุด พฤติกรรมของ API ใช้ Bruno แบบ black-box เป็น seam หลัก

**เสร็จเมื่อ:** ผู้ใช้ยืนยัน seam แล้ว และ spec มีครบ: user stories, implementation decisions, testing decisions, out of scope

## 3. Tickets

เรียก `to-tickets` แบ่งเป็น **tracer bullet** ใส่เส้น blocked-by ให้ผู้ใช้ยืนยันขนาดก่อน เขียนเป็นไฟล์ `docs/specs/<ชื่อ>/NN-slug.md` เกณฑ์ของทุก ticket มีสามกลุ่ม: test ของตัวเอง, request ใน Bruno และเกณฑ์ของผู้ดำเนินการ ("deploy แล้ว `bru run` ผ่านทั้งชุด") งานเตรียม (prefactor) มาก่อน ticket ที่มีเรื่องรอผู้ใช้ตัดสินเป็น `needs-decision` ไม่ใช่ `ready-for-agent`

**เสร็จเมื่อ:** ผู้ใช้อนุมัติการแบ่ง และทุก ticket มีเกณฑ์ที่ตรวจได้ทีละข้อ

## 4. Implement

เรียก `implement-spec` แตก integration branch จาก `main` คัดลอก `implementer-guide.md` ไปไว้ใน scratchpad แล้วเติมค่า เปิด subagent หนึ่งตัวต่อ ticket ใน frontier แต่ละตัวทำใน worktree ของตัวเอง implementer **ไม่ deploy ไม่ push และไม่รัน Bruno กับ Mini PC** ผู้ดำเนินการเป็นคน merge และรัน build กับ test **หลัง merge ทุกครั้ง** เพราะ merge ที่ไม่ conflict ยังพังตอน compile ได้

**เสร็จเมื่อ:** ทุก ticket ถูก merge และโค้ดที่ merge ครบผ่าน vet, test, lint, fmt, vitest, eslint และ build โดยอ่านผลทุกบรรทัด (exit 0 ของคำสั่งครอบไม่ใช่หลักฐาน)

คุมภาระ Mini PC และ usage limit ตาม `environment.md` หัวข้อ "ภาระเครื่อง"

## 5. Review

เรียก `code-review` ระดับ `high` กับ branch จัดทุกข้อที่เจอเป็นหนึ่งในสี่: แก้ตอนนี้ · ticket รอตัดสินใจ · ticket ที่เลื่อนพร้อมเงื่อนไขกลับมาทำ · ตัดสินใจไว้แล้วว่าไม่แก้ (อ้างตำแหน่งใน spec) แล้วให้ subagent ตัวเดียวแก้กลุ่มแรก

**เสร็จเมื่อ:** ทุกข้อมีผลจัดกลุ่มที่เขียนไว้ และกลุ่มแก้ตอนนี้ถูก merge และผ่านการตรวจซ้ำ

## 6. Deploy ครั้งเดียว

เขียนโค้ดให้เสร็จทั้งหมดก่อน แล้ว deploy หนึ่งครั้ง: push branch, สลับ checkout บน Mini PC, `up --build -d` ตาม `environment.md` ขออนุญาตผู้ใช้ก่อนสร้าง database หรือ volume และก่อนแตะ container ที่ไม่ใช่ของงานนี้

**เสร็จเมื่อ:** container ขึ้นครบ, migration เป็นเวอร์ชันที่คาด, `/readyz` ตอบ 200 และเห็นบรรทัด log ของพฤติกรรมใหม่ตอน start

## 7. พิสูจน์

รัน Bruno ทั้งชุดพร้อมสคริปต์ restart แล้วตรวจในเบราว์เซอร์ ตาม `testing.md` การตรวจนับเป็นหลักฐานก็ต่อเมื่อมันมีโอกาสล้มได้: สถานะที่รอดูการเปลี่ยนต้องอยู่นานพอให้เห็น และคำเตือนจากสคริปต์แปลว่า **ยังไม่พิสูจน์**

**เสร็จเมื่อ:** ทุกเกณฑ์ของ ticket มีหลักฐาน และทุก ✗ ถูกอธิบายว่าเป็นความผิดของสคริปต์ (รันซ้ำแล้วผ่าน) หรือของระบบ (เปิด ticket)

## 8. ปิดงาน

ติ๊กเกณฑ์พร้อมบรรทัด `Verified` (commit, ตัวเลข, วันที่) อัปเดตเอกสารที่พูดถึงพฤติกรรมที่เปลี่ยน ลบข้อมูลทดสอบด้วย ID ตรงตัวหรือ prefix ของตัวเองพร้อมเงื่อนไขกันพลาด ลบ worktree และ branch ชั่วคราว

**เสร็จเมื่อ:** ไม่มีข้อมูลทดสอบเหลือใน Temporal, ฐานข้อมูลและ Schedule, working tree สะอาด และ branch ชั่วคราวหมด

## 9. ส่งมอบ

ให้ข้อความ commit และเนื้อหา PR (skill `pr`) ผู้ใช้เป็นคน merge เมื่อ merge แล้ว ตรวจว่าความต่างระหว่างที่ deploy อยู่กับ `main` เป็นเอกสารล้วน จึงสลับ Mini PC กลับ `main` และ pull

**เสร็จเมื่อ:** Mini PC อยู่ที่ `main` และ `main` ในเครื่องตรงกับ `origin/main`

## วิธีรายงาน

บอกสิ่งที่ตรวจแล้วกับสิ่งที่ยังไม่ได้ตรวจแยกกัน ทุกการตัดสินใจที่ทำแทนผู้ใช้ต้องบันทึกไว้ในที่ที่ผู้ใช้อ่านพร้อมทางย้อนกลับ ขออนุญาตก่อนทำสิ่งที่กระทบนอกเครื่อง (push, deploy, ลบ branch บน GitHub) เมื่อเห็นการขัดจังหวะโดยไม่มีข้อความตามมา ให้หยุดเฉพาะงานที่กระทบนอกเครื่องแล้วถามหนึ่งข้อ
